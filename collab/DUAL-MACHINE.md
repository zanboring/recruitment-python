## 三、硬规则（每条都对应一次真实事故或已识别的风险）

1. **开工前先 `git pull --ff-only`；收工后立刻 `git push`。**
   不允许"攒着之后再推" —— 曾发生过台式机积压 **9 个提交**未推的情况
   （2026-10-11 16:08 已全部推送成功），这会直接导致两台机器分叉。
   **同一时间只允许一台机器在提交**；切换机器前务必先 push。
2. **禁止用拷贝/U盘/网盘直接搬工作目录**（绕过 git）。
   本项目历史上已因"两份带 `.git` 的活副本指向同一 origin"翻过车。
3. **分支纪律**：`dev-codebuddy` / `dev-trae` / `dev-workbuddy`，各人只能用自己那条。
   commit 前 `git rev-parse --abbrev-ref HEAD`，commit 后 `git log --oneline -1` 复核。
4. **禁止 `git add -A`** —— 工作树里常有他人未提交内容。
5. **台式机只拉 `main`**，不拉 `dev-*`。
   理由：未验收的代码不应进入运行环境。`main` 是"已验证"的边界。
6. **任何超过 1 分钟的操作（全量测试、构建）之前与之后，都重新确认分支与 `git status`。**

## 四、识别到的最大风险：写者从 2 个变成「2 台机器 × N 个 agent」

原来的结构里"单目录共享 HEAD + 两个 AI 并发"已经造成过**两次分支错位事故**。
引入第二台机器后，写者变成 **2 台机器 × 各自的 agent**，且**工作树不再共享**——
这意味&#x7740;**"分支错位"会被"跨机分叉"取代**，后者更难发现也更容易丢工作。

**缓解手段（必须执行）：**

- 一台机器一个角色（见 §一），不做"两边都开发"
- 串行：同一时间只允许一台机器在提交
- 每天开始与结束时各 sync 一次（`pull` / `push`）
- 定期用 `git log --oneline --all --graph` 核对是否出现意外分叉

## 五、网络注意（实测，2026-10-11）

| 目标                                   | 台式机可达性      | 说明                                  |
| ------------------------------------ | ----------- | ----------------------------------- |
| `github.com` / `codeload.github.com` | ✅ 200 / 301 | **`git push` / `git pull` 可正常走这条路** |
| `api.github.com`                     | ✅ 200       |                                     |
| `objects.githubusercontent.com`      | ❌ 000       | **只有 release 二进制资产被墙**              |

- **只要下载 GitHub 上的二进制文件**（Docker 镜像、Playwright、WSL 包等），才需要加加速前缀 `https://gh-proxy.com/`。

  **推送必须由用户在真实终端执行**，不要在沙箱里反复重试。

## 七、硬件资源图与 GPU 分工（2026-10-11 实测）

### 7.1 两台机器的真实规格

| 资源               | 笔记本 ROG 5R                         | 台式机（本机）                         |
| ---------------- | ---------------------------------- | ------------------------------- |
| CPU              | Ryzen 9 **5900HX**（8C/16T）         | **i5-14600KF（14C/20T）** ← 更强    |
| 内存               | **32 GB**                          | **32 GB**（实测总量 31.8 GB）         |
| GPU              | **RX 6800M（RDNA2 / gfx1031）12 GB** | **RTX 5060 Ti 8 GB**（驱动 617.14） |
| 推理速度（7–8B Q4 量级） | Vulkan 约 **14 tok/s**              | CUDA 约 **25 tok/s**             |
| 显存优势             | ✅ **12 GB > 8 GB**，能装更大的模型         | CUDA 生态成熟，更快                    |

### 7.2 结论：两台是**互补**，不是主从

- **台式机赢在**：CPU 核多（适合重编译）、CUDA 生态成熟（快约 40–80%）、外接大屏
- **笔记本赢在**：**显存更多**、内存不会被游戏挤占、**可完全独立工作**

所以主从模型（"笔记本只开发、台式机只运行"）是错的——**它浪费了笔记本的算力**。

### 7.3 ⚠️ Ollama 在 AMD 上的现实（已核实官方文档）

- Ollama 官方 **Windows (ROCm) 支持清单**里只有**桌面版** `6800 / 6800 XT`，
  **没有移动版 `6800M`（gfx1031）**
- `HSA_OVERRIDE_GFX_VERSION` 官方只给了 **Linux** 的说明
- 因此笔记本（Windows）上跑 Ollama GPU 加速，**可靠性排序**：

| 方案                                | 评价                                                                                           |
| --------------------------------- | -------------------------------------------------------------------------------------------- |
| **Vulkan 后端**                     | 首选。llama.cpp / LM Studio 在 Windows+AMD 上的默认路径；第三方资料称 Ollama 有实验性 `OLLAMA_VULKAN=1`，**需实测确认** |
| ROCm + `HSA_OVERRIDE_GFX_VERSION` | 折腾成本高，不推荐                                                                                    |
| **纯 CPU**                         | **可接受**——项目用的模型很小（`qwen3.5:4b` + `qwen3-embedding:0.6b`）

> **✅ 用户实测补充（2026-10-11）**：笔记本**之前就是本项目的开发机**，Ollama 已装，
> **qwen 系列模型实测可用**。所以笔记本在 AI 这一环是**自给自足**的，
> 上一轮"AMD 可能跑不了 Ollama"的担忧**不成立**。
>
> ⚠️ **待用户核实的一点**：它跑的是 **GPU 还是 CPU**？在笔记本上执行 `ollama ps`，
> 看 `PROCESSOR` 一列。若显示 `100% CPU`，说明 6800M 实际没被用上
> （与官方清单不含 `6800M` 一致），速度会慢 5–10 倍。
> **对本项目无影响**（4B + 0.6B 太小，CPU 够用），但决定你以后跑大模型时的预期。                                     |

### 7.4 分工规则

- **台式机空闲** → 项目与 Ollama 都在台式机（CUDA 更快，且模型与项目同机无网络开销）
- **台式机在打游戏/看电视** → **笔记本独立跑全栈** + 自己的 Ollama（Vulkan 或 CPU）
- ❌ **不要在台式机打游戏时同时跑 Docker 全栈 + Ollama** —— 32 GB 内存被三方争抢，游戏会掉帧
- ❌ **不要试图把两台机器的内存/显存"合并"** —— 千兆局域网带宽远低于显存带宽，分布式推理不现实

### 7.5 笔记本的一次性准备

1. 装 Docker Desktop（**必须选 WSL2 后端**）+ 配 `registry-mirrors`（本机实测 Docker Hub 不通）
2. 装 Ollama，实测 `OLLAMA_VULKAN=1` 是否生效（用 `ollama ps` 看模型是否落在 GPU）
3. 跑项目栈：
   `PLAYWRIGHT_DOWNLOAD_HOST=https://cdn.npmmirror.com/binaries/playwright docker compose --env-file config.env up -d --build`
4. 笔记本上 Ollama 的模型名要与项目 `.env` 对齐：`qwen3.5:4b` 与 `qwen3-embedding:0.6b`

## 八、环境一致性与云 agent 接入（2026-10-11）

### 8.1 ⚠️ 已存在的不一致：源码模式 vs 容器模式

| 环境 | Python 版本 |
|---|---|
| 源码模式（`.venv`） | **3.14.7** |
| 容器模式（`docker/backend/Dockerfile`） | **3.11** |

**差 3 个大版本，而项目没有任何版本声明** —— 没有 `.python-version`、没有 `requires-python`、
没有 `pyproject.toml`；Node 侧同样没有（容器固定 `node:20-alpine`）。

**后果**：代码若用了 3.12+ 语法（`type X = ...`、PEP 695 泛型、3.12 的 f-string 解析变化等），
**本地 3.14 跑得通，容器 3.11 直接 `SyntaxError`**。
这就是"本地能跑、换环境就炸"—— 而且**不需要两台机器，一台机器内部就能复现**。

> **规则：以容器为唯一「运行真源」，所有代码必须兼容 Python 3.11。**
> 源码模式（`.venv` 3.14）只作**快速单测**用途；
> **"3.14 通过" ≠ "3.11 通过"** —— 凡涉及语法或标准库的判断，一律以容器为准。

### 8.2 三类编码活动，三种统一手段（不要用同一个办法套）

| 编码活动 | 环境复杂度 | 统一手段 | 为什么 |
|---|---|---|---|
| 算法 / 力扣练习 | 极低（解释器 + 标准库） | **统一解释器版本**即可 | 为跑一个 `two_sum.py` 起容器，启动开销会拖节奏；力扣判题本就在云端 |
| 项目写代码 + 跑单测 | 中（Python 依赖） | 同一个 `requirements.txt`；**以容器内 pytest 为准** | 锁文件 + 容器，双重保险 |
| 项目全栈运行 | 高（前端构建 + Playwright + Redis + nginx） | **同一份 `docker-compose.yml` 各自 build** | ✅ 已达成，A7/A8 验收通过 |

**结论**：你最初担心的"两台机器环境不一致"，在最重的那一档（全栈运行）**已经解决了**。
剩下真正会不一致的是**解释器版本**，而解决它只需要"声明 + 遵守"，不需要 Docker。

### 8.3 云 agent 的接入约定（⚠️ 风险不在环境，在**分叉**）

云 agent 会引入**第三份代码副本**：

- 云 agent 有自己的沙箱 → 代码副本从 **2 份变 3 份**
- 云 agent **看不到 `.env` / `config.env`（gitignored）** → 它能写代码，但**跑不了项目**
- 因此它的权限必须被限死：

> **云 agent 只允许：写代码 → 推自己的 `dev-cloud` 分支。**
> **禁止**：直接推 `main`、改 `collab/**`（协作信道）、改容器配置。
> 本机 `git pull dev-cloud` 后，**必须在容器里跑一遍**才能合并 ——
> 因为云 agent 无法验证它写的代码能否在 3.11 容器里跑起来。

### 8.4 本地模型必须在两台机器上保持一致（**嵌入模型尤其**）

项目的 `.env` 把模型名写死了：

| 用途 | 模型名 | 能否换 |
|---|---|---|
| 对话 / 分析 | `qwen3.5:4b` | 换则**两台都要改 `.env`** |
| 代码 | `qwen3.5:4b` | 同上 |
| 工具选择 | （留空） | — |
| **向量嵌入** | `qwen3-embedding:0.6b` | ⚠️ **强烈不建议换** |

**为什么嵌入模型尤其不能换**：向量空间是模型**特有**的。
`*.db` 虽被 `.gitignore` 挡住（各机各自一份知识库），但只要**任何一次把
`data/recruitment.db` 带到另一台机器**，换了嵌入模型的那台就会检索出垃圾结果 ——
而且是**静默的**：不报错、不崩溃，只是答案变差。

**怎么装：不要重新 `ollama pull`，直接从另一台机器拷 `models/` 目录** ——
字节完全一致，且比走 Ollama registry 快得多：

```
robocopy "\\192.168.31.74\D$\Apps\Data\Ollama\models" "<笔记本目标路径>\models" /E /COPY:DAT /R:2 /W:2
```

（台式机现有内容：`blobs/` **8 个文件 / 3.7 GB** +
`manifests/registry.ollama.ai/library/{qwen3.5/4b, qwen3-embedding/0.6b}` + `metadata/`。
拷贝后把笔记本的 `OLLAMA_MODELS` 指向该目录，与台式机保持一致。）

**可选增强**：笔记本 12 GB 显存可以**额外**装一个更大的模型（如 14B Q4 ≈ 9 GB）供自己使用，
但它**不能替代**上面两个 —— 项目的 `.env` 只认模型名。
前提：先确认 `ollama ps` 显示的是 **GPU 而非 CPU**，否则 14B 会慢到不可用。

## 九、多 agent 与「同一个账号」的现实（2026-10-11 实测）

> 背景：用户认为"两台机器的 agent 用同一个账号，所以很简单"。
> **实测结论：同账号解决的是"身份"，不是"代码"。**

### 9.1 同账号能给什么、给不了什么

| | 同一个账号 | 说明 |
|---|---|---|
| 登录态 / 额度 / 云端设置 | ✅ 能给 | |
| **磁盘上的代码** | ❌ **给不了** | 代码在工作目录里，只能靠 git 同步 |
| **本地会话历史** | ❌ **给不了** | **会话是按「本地文件系统路径」建索引的** |

**实测证据**：

- `~/.workbuddy/projects/c-Users-Administrator-**Desktop-recruitment-python**/*.jsonl`
  —— 目录名就是"本地路径"的转写。**换一台机器、路径变了，历史会话不会跟过来**，哪怕账号完全相同。
- `~/.workbuddy` 本地状态 **5.6 GB**（会话 / 日志 / 缓存），**不通过账号同步**。

> 所以：**同账号 ≠ 同工作区**。代码一致性仍然只能由 Git 保证。

### 9.2 实际 agent 数量比预估的多

本机实测已装 **4 个桌面客户端**：`CodeBuddy CN`、`Trae CN`、`TRAE SOLO CN`、`豆包`（另有 WorkBuddy）。

→ **写者数量 = 2 台机器 × N 个 agent**，远超过此前估计的"4 个"。
**所以「每个 agent 一条分支」不是可选项，是必需项。**

### 9.3 ⚠️ 同账号引入的一个**新的隐蔽风险**

当**同一个账号的 agent 在两台机器上同时打开同一个项目**时：

- 云端会话 / 记忆是**共享**的，但**文件是两份**
- 它可能依据「云端记忆里的代码」给出建议，而那份代码**与当前磁盘上的不一致**
- 结果：**看起来一切都对，但改出来的东西对不上** —— 比"分支错位"更难发现

**规则**：

> **同一个 agent 不要在两台机器上同时打开同一个项目。**
> **换机器前先 `commit` + `push`** —— 让云端状态和磁盘状态重新对齐。

## 十、分支命名策略与「笔记本旧副本」处置（2026-10-11）

### 10.1 结论：分支按「agent」分，**不按「机器」分**

**用户提议**：每个软件 × 每个平台一条分支（如 `dev-codebuddy-pc` / `dev-codebuddy-laptop`），
4 agent × 2 平台 = **8 条**。

**评估：不采纳。** 四条理由：

1. **分支数爆炸**：8 条长期分支 → 合并到 `main` 的合并点从 3 个变 8 个，
   冲突概率与维护成本同步上升
2. **它没解决真正的问题**：分叉的根源是"两个写者同时改同一批文件"；
   按平台拆分支**不减少并发**，只增加分叉线
3. **⚠️ 它会"合法化"最危险的场景**：同一个 agent 在两台机器上同时干活 ——
   这正是 §9.3 警告的情况（云端记忆共享、文件两份）。
   **给它两条分支，等于默认允许这件事发生**
4. **与实际约束不匹配**：一个人同一时间只在一台机器上
   → **平台维度天然互斥**，不需要在分支上表达

**采用方案**：分支仍为 3 条 —— `dev-codebuddy` / `dev-trae` / `dev-workbuddy`；
**机器身份放进 commit message 的 trailer**：

```
fix(docker): 修复 CORS_ORIGINS 类型不匹配

[machine: pc] [agent: workbuddy]
```

**若要自动化（可选）**：台式机 `git config user.name "zanboring (PC)"`、
笔记本 `git config user.name "zanboring (Laptop)"` → 每条提交自动带机器名。
⚠️ **代价：作者名变了**（`git log` 与 GitHub 上会出现两个名字）。
**portfolio 项目慎用** —— 面试官看到的作者名不一致会显得随意。

**若确实需要平台维度** → 用**短生命周期任务分支**（干完即合、即删）：
`wip/pc-codebuddy-redis-quota`，而不是 8 条长期分支。

### 10.2 ⚠️ 笔记本上的旧副本必须先处置（高优先级）

用户说明「**笔记本之前就是开发这个项目的**」
→ **笔记本上很可能存在一份带 `.git` 的旧副本**。

**这正是本项目历史上翻过车的地方**：桌面那份过期快照与主仓库 `.git` 相同、`origin` 相同
→ 在其上提交并 push 会与本仓库历史打架。

**动手前必做**（在笔记本上执行四条）：

```
git log --oneline -12      # 有没有未推送的本地提交？
git status --short         # 有没有未提交改动？
git stash list             # 有没有 stash？
git remote -v              # 指向哪个 origin？
```

| 检查结果 | 处置 |
|---|---|
| **有未推送内容**（本地提交 / 改动 / stash） | 先 `git push origin HEAD:rescue/laptop-legacy` **保住**，再重新 clone |
| **干净且与 `origin` 一致** | 直接删掉旧副本，重新 clone |
| 任何情况 | ❌ **禁止**直接在旧副本上继续开发 —— 会重演历史事故 |
